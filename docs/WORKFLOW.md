# 작업 방식 (브랜치·커밋·병합)

지금까지의 프로토타입 작업은 기본 브랜치에 직접 쌓았다. **앞으로는 모든 작업을 주제별 브랜치에서 하고, 커밋 내역을 읽기 쉽게 유지한다.**

## 브랜치
- 기본 브랜치에서 따서 만든다: `feat/<주제>`, `fix/<주제>`, `docs/<주제>`, `chore/<주제>` (예: `feat/essence-system`, `fix/ranged-retreat`).
- 한 브랜치는 한 가지 주제만 다룬다. 끝나면 병합하고 지운다.
- 기본 브랜치에는 직접 커밋하지 않는다. 다른 사람이 쓰는 브랜치의 히스토리는 다시 쓰지 않는다(리베이스·강제 푸시 금지).

## 커밋
- 제목은 한 줄, 명령형, 72자 이내, 접두어로 종류를 밝힌다: `feat:` `fix:` `docs:` `test:` `refactor:` `chore:`
- 본문에는 **왜** 바꿨는지와 눈에 띄는 영향(수치 변경, 규칙 변경)을 적는다.
- 한 커밋 = 한 논리적 변경. 코드와 그에 맞는 테스트·문서는 같은 커밋에 둔다.
- 푸시 전에 전부 통과해야 한다:
  - `python3 -m unittest discover -s tests -t .`
  - `node --test web/tests/game.test.js` · `node web/tests/parity.js`
  - `python3 web/build.py && node web/tests/e2e.js` (UI 를 건드렸을 때)

## 병합 (PR)
- PR 은 사용자가 요청할 때만 만든다. 본문은 **목적 / 변경 / 검증 / 남은 것** 순서로 쓴다.
- 기본은 **스쿼시 병합**: 주제 하나가 기본 브랜치에 커밋 하나로 남는다. 제목은 위 커밋 규칙을 따르고, 본문에 변경 요약을 넣는다.
- 병합할 때마다 `CHANGELOG.md` 에 한두 줄을 추가한다. 규칙·수치가 바뀌면 `docs/implementation_notes.md` 도 함께 갱신한다.
